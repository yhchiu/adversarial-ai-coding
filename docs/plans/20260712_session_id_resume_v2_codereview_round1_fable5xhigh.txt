❯ 請說明為什麼應該要擋 codex  --sandbox  and agy --continue=<value>

● 好問題,兩者被擋的理由不同——--sandbox 是「會弄壞 argv 且動搖 workflow 的執行前提」,--continue= 是「同一個危險旗標的另一種拼法」。分開說明:

為什麼擋 codex --sandbox

1. exec resume 根本不接受這個旗標,會讓 run 跑到一半才炸。
Workflow 有兩種 argv 形狀:fresh 用 codex exec --sandbox workspace-write ...,resume 用 codex exec resume -c sandbox_mode="..." ...——之所以 resume 改用 -c,正是因為
resume 子命令沒有 --sandbox 旗標(計畫與 bash 版註解都記了這點)。如果放行 CODEX_ARGS='--sandbox read-only',第一輪 fresh call 也許能跑,但第二輪起的每個 resume call
都會因為未知旗標直接 CLI error。這種錯誤最糟的地方是延遲引爆:燒完第一輪昂貴的 AI call 之後才死,而且死狀是難以歸因的 agent failure。Preflight
在啟動時就擋下、給明確訊息,是拿「立刻可修的錯誤」換「跑一半的莫名失敗」。

2. Fresh call 上會跟 workflow 自己的 --sandbox workspace-write 重複。
重複旗標的下場二選一:CLI 報「不可重複」錯誤(又是難歸因的失敗),或後者靜默覆蓋前者。後者更糟——sandbox 模式是 workflow 正確性的前提:worker 必須能寫 workspace(否則 review
loop 會在「worker 說做完了但沒有任何變更」的狀態空轉);反方向若被覆蓋成 danger-full-access,實際執行的安全邊界跟 README 和 archive metadata
宣稱的完全不同,而且沒有任何紀錄顯示這件事發生了。

3. 原則層面:這是 workflow 的功能參數,不是 agent 的口味參數。
CODEX_ARGS 的定位是「調整 agent 行為」(模型、reasoning effort 等),而 sandbox 模式決定的是 workflow 自身的運作前提。如果真有「我想用不同 sandbox
政策」的需求,正確做法是開一個顯式的 workflow 設定(例如未來加 SANDBOX= 環境變數),讓它同時套用到 fresh 和 resume 兩種 argv 形狀、寫進 metadata——而不是從 pass-through
args 偷渡進去,因為 pass-through 有一半的呼叫路徑(resume)根本表達不了它。

為什麼擋 agy --continue=<value>

1. --continue 的語意正是這整個計畫要消滅的東西。
--continue 是「續接最近一次 conversation」——全域 recency resume。計畫的 invariant 2 明文禁止它,因為互審流程中 worker 和 reviewer 交錯執行,「最近一次」在 review
輪之後指向的是 reviewer 的 conversation。若使用者把它塞進 AGY_ARGS(而 AGY_ARGS 是按命令共用、worker 和 reviewer 的每一次呼叫都會帶上):

- worker 的 fresh call 會靜默接上 reviewer 的舊對話——正是這個 feature 要根除的 cross-contamination;更糟的是 workflow 接著從 log 解析出的 id 就是 reviewer 的
conversation id,依「已知 id 只升級」規則永久收編,之後每一輪都精準地 resume 到錯的 session。
- worker 的 resume call 會同時帶 workflow 的 --conversation <uuid> 和使用者的 --continue,兩者衝突、優先序未定義,exact-id 保證直接作廢。
- reviewer call 帶上 --continue 則讓本應每輪全新、獨立的 reviewer 繼承 worker 的對話脈絡,破壞互審的對抗性前提。

2. = 形式只是同一個旗標的另一種拼法,不擋等於白擋。
現有 blocklist 是字串比對:--continue=true 不等於 --continue,所以直接漏過。程式碼其實已經意識到這個問題——它對 --log-file= 和 --conversation= 都擋了前綴形式,唯獨漏了
--continue=,這是同一道 guard 內部的不一致。許多 CLI parser 同時接受 --flag value 和 --flag=value 兩種寫法;只要 agy(或它未來的版本)接受 = 形式,上面第 1
點的所有後果原封不動地發生。

3. 擋它的成本是零。
--continue 本體已被保留,所以 --continue=<anything> 在 AGY_ARGS 裡不存在任何合法用途——不會誤殺任何人。就算 agy 實際上不接受 =
形式(我沒有實測確認這點),擋下它也只是把「跑到一半 agy
報未知旗標」提前成「啟動時給明確訊息」,依然是純收益。這就是為什麼我把它歸在「防禦性、一行」:不是因為確定有人會踩,而是補齊同一道 guard 的對稱性,順便對 agy 升版免疫。

共同的判準:這道 preflight 擋的不是「使用者不該調的參數」,而是「會奪走 workflow 賴以維持保證的控制通道」——session 定址(resume/--continue/--conversation)、id
解析來源(--log-file)、輸出格式(--json)、執行邊界(--sandbox/sandbox_mode)。--sandbox 和 --continue= 各踩其中一條,所以都該擋。
